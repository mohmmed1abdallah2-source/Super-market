**المشروع:** Global Enterprise Supermarket & Retail ERP  
**المستودع:** `mohmmed1abdallah2-source/Super-market`  
**فرع العمل الحالي وقت إعداد هذه الوثيقة:** `feature/multi-store-isolation-foundation`  
**آخر نقطة مرجعية قبل توثيق هذه الوثيقة:** `ca7b77cb69e8e962299e190454bad4d0090fbc98`  
**تاريخ التحديث:** 2026-11-11

> هذه الوثيقة هي لوحة الحالة الرئيسية للمشروع. تصف ما وجدناه في ملفات المستودع وما أُضيف إليه، وتفصل ذلك عن الأعمال التي لم تنفذ أو لم تختبر. نتائج Neon المتعلقة بالتنفيذ وعدد الجداول مبنية على إفادة المستخدم، وليست قراءة مباشرة من حساب Neon.

## 1. ملخص تنفيذي

المشروع تطبيق Flutter لإدارة سوبرماركت ونقاط بيع ومخزون وحسابات مبسطة للأطراف، مع تشغيل محلي Offline-first ومزامنة. يحتوي المستودع على تطبيق Flutter محلي، ومكونات POS ودفتر وسندات، وخدمات Firebase/Firestore، وطبقة API مكتوبة بـ Dart/Shelf، وعقود مشتركة وعميل HTTP، وترحيلات PostgreSQL، واختبارات وCI، ووثائق معمارية، وقوالب PDF.

**الحالة الواقعية:** توجد أجزاء برمجية ووثائق تأسيسية في المستودع، لكن لا يوجد حتى تاريخ هذه الوثيقة إثبات موثق لاكتمال بناء التطبيق أو نشر API أو الربط الحي بين Flutter وNeon أو تنفيذ عزل المتاجر المتعدد. نجاح ملفات SQL في Neon وعدد 18 جدولًا أبلغ عنهما المستخدم. لا يعني ذلك أن التطبيق متصل أو أن بيئة الإنتاج جاهزة.

## 2. نطاق المنتج والقرارات المعتمدة

- تطبيق إدارة سوبرماركت وبيع مباشر داخل المتجر؛ ليس متجرًا إلكترونيًا.
- واجهة عربية RTL مع وضع داكن.
- POS متعدد الفواتير، كتالوج أصناف، وحدات متعددة، باركود عادي وباركود ميزان.
- مخزون محلي، دفتر «له وعليه»، سندات قبض وصرف، قيود محاسبية، صناديق ومحافظ، تقارير وطباعة.
- البيع يجب أن يعمل دون إنترنت، ويُحفظ محليًا في SQLite داخل معاملة واحدة تشمل العناصر المالية والمخزنية وطابور المزامنة.
- Windows وAndroid وWeb ضمن هدف التشغيل؛ Web يحتاج محول تخزين محلي متوافقًا مثل IndexedDB، ولا نعتبره منجزًا بمجرد ذكره في وثيقة.
- يجب أن تتزامن بيانات المتجر نفسه بين الأجهزة بعد عودة الاتصال. العمليات غير المتصلة تبقى محلية ومعلقة حتى المزامنة؛ لا يوجد ضمان ظهور فوري أثناء انقطاع الشبكة.
- متطلب تعدد المتاجر: حساب مالك واحد يستطيع الوصول إلى عدة متاجر، وكل متجر معزول تمامًا. القرار المعماري المستهدف هو قاعدة PostgreSQL مستقلة ودور قاعدة بيانات مستقل لكل متجر، مع قاعدة تحكم منفصلة للهويات ودليل المتاجر والعضويات. `branch_id` يظل فرعًا/موقعًا داخل المتجر ولا يصبح هوية المتجر.
- الميزانية التشغيلية المستهدفة صفر شهريًا؛ أي خيار مجاني يجب التحقق من حدوده وسياسة الخمول والانتهاء والقيود، ولا يوجد ضمان SLA مجاني.
- الحفاظ على قاعدة SQLite الحالية وبيانات المستخدم شرط إلزامي؛ لا حذف أو استبدال أو نقل مدمر.

## 3. ما هو موجود في المستودع — جرد حسب المجال

### 3.1 تطبيق Flutter والواجهة
- نقطة التشغيل: `lib/main.dart`.
- واجهة رئيسية: `lib/screens/app_shell.dart`.
- لوحة التحكم: `lib/screens/dashboard/s02_executive_dashboard_screen.dart`.
- شاشة POS: `lib/screens/pos/s03_supermarket_pos_screen.dart`.
- شاشة المنتجات متعددة الوحدات: `lib/screens/catalog/s08_products_multi_unit_screen.dart`.
- شاشة الأطراف والسندات: `lib/screens/accounts/s19_parties_and_vouchers_screen.dart`.
- ثيم داكن ومكونات مشتركة ضمن `lib/core/`.
- مزودات الحالة في `lib/providers/`.
- هذه قائمة بالملفات الموجودة، وليست شهادة قبول وظيفي لكل شاشة أو ميزة.

### 3.2 قاعدة البيانات المحلية والعمليات
- `lib/data/database/database_helper.dart` لإدارة اتصال SQLite.
- `lib/data/database/schema_builder.dart` لبناء مخطط SQLite.
- `lib/data/database/seed_data.dart` لبيانات التطوير الأولية.
- نماذج الأصناف والوحدات والدفتر والمزامنة في `lib/data/models/`.
- خدمات POS والباركود والترحيل في `lib/data/services/`.
- يلزم فحص الكود والاختبارات للتأكد من السلوك على كل منصة، ولا يكفي وجود الملفات.

### 3.3 المزامنة الحالية
- واجهة النقل `ISyncTransport` موجودة.
- توجد خدمة Firebase/Firestore ضمن `lib/data/services/firebase_free_tier_sync_service.dart`.
- قواعد Firestore موجودة في `firestore.rules`.
- وجود التكامل في المصدر لا يثبت إعداد مشروع Firebase حقيقي أو نشر القواعد أو تهيئة Authentication/Custom Claims.
- توجد بنية API/Sync بديلة على PostgreSQL، لكن Flutter لم يُثبت بعد أنه يستخدمها في جلسة فعلية.

### 3.4 PDF والطباعة
- قالب التقرير الرسمي: `lib/core/pdf/official_report_template.dart`.
- منشئ الإيصالات وكشوف الحساب: `lib/core/pdf/receipt_and_ledger_pdf_builder.dart`.
- خطوط Noto Naskh Arabic Regular/Bold موجودة في `assets/fonts/`.
- يوجد اختبار قالب PDF في `test/official_report_template_test.dart`.
- ملف الشعار الحالي placeholder شفاف وليس شعار المتجر النهائي.
- يلزم التحقق الفعلي من إخراج PDF العربي على Android وWindows وWeb والطباعة والطابعات الحرارية.

### 3.5 API والخادم
- خادم Dart/Shelf في `server/bin/server.dart`.
- وحدات المبيعات والمزامنة والدفتر موزعة بين domain/application/data/presentation.
- عميل API في `packages/api_client/`.
- العقود المشتركة في `packages/core_contracts/`.
- عقد OpenAPI في `docs/openapi_v1.yaml`.
- الإعداد الحالي للخادم يعتمد متغيرات PGHOST/PGPORT/PGDATABASE/PGUSER/PGPASSWORD، ويستخدم نموذج رمز فرع؛ لا يوجد في هذا وحده نظام تسجيل مالك/عضويات ومتاجر متعددة.
- لا يوجد إثبات أن الخادم منشور على استضافة عامة أو يعمل بعنوان HTTPS.

### 3.6 PostgreSQL وNeon
- ملفات الترحيل الأصلية للاختبار والتطوير: `server/migrations/20261109_001_erp_core.sql` و`server/migrations/20261109_002_pos_sales_and_lah_alayh_ledger.sql`. تحتوي هذه الملفات على seed data.
- نسخ Neon schema-only التشغيلية: `docs/neon/001_erp_core_schema_only.sql` و`docs/neon/002_pos_ledger_schema_only.sql`. لا تخلط بينها وبين الترحيلات الأصلية.
- المستخدم أفاد بإنشاء Neon project `supermarket-erp` وتشغيل اختبار الاتصال بنجاح، ثم تنفيذ نسختي schema-only بنجاح وظهور 18 جدولًا. لم يتم فحص لوحة Neon أو مخرجات الاستعلامات مباشرة من جانبنا.
- لا تتضمن نسخ schema-only بيانات دليل الحسابات الافتراضي أو الصناديق والمحافظ؛ هذه الجداول منشأة لكن يلزم إعداد بيانات تأسيسية مدروسة قبل العمليات المحاسبية الفعلية.
- لم يتم توثيق دور تطبيق محدود الصلاحيات أو فحص TLS أو backup/restore.

### 3.7 الاختبارات وCI
- توجد اختبارات Flutter ضمن `test/`.
- توجد اختبارات خادم PostgreSQL ضمن `server/test/`.
- يوجد GitHub Actions workflow: `.github/workflows/flutter-validation.yml`.
- وجود الاختبارات وملف CI لا يساوي نجاحها. لا تسجل هذه الوثيقة نجاح analyze/test/build إلا عند توفر سجل تشغيل ناجح فعليًا.

## 4. ما تم إنجازه في هذه الجلسة/المرحلة

1. مراجعة جرد المستودع والفرع الحالي وملفات السجل والوثائق الرئيسية.
2. إنشاء نسختين schema-only من الترحيلين الأصليين تحت `docs/neon/` دون تغيير الترحيلات الأصلية.
3. إزالة إدخالات بيانات التطوير من نسخ Neon التشغيلية، بما فيها الفرع/المستخدم/المنتجات/الأطراف التجريبية، وكذلك إدخالات دليل الحسابات والصناديق الافتراضية.
4. المستخدم نفّذ SQL test في Neon وأفاد بنجاحه.
5. المستخدم نفّذ الترحيلين schema-only وأفاد بنجاحهما، وأفاد بأن استعلام الجداول أعاد 18 جدولًا.
6. إنشاء `docs/neon/NEON_SETUP_PROGRESS.md` لتوثيق تفاصيل Neon وما تبقى.
7. تحديث `docs/CHANGELOG.md` لتسجيل إضافة نسخ Neon والتوثيق.
8. إعداد هذه الوثيقة لتكون لوحة الحالة الشاملة لكل المشروع، لا Neon فقط.

**حدود التحقق:** الخطوات 4 و5 هي نتائج أبلغ عنها المستخدم. لا نزعم أننا نفذنا SQL من داخل Neon أو تحققنا من الجداول مباشرة.
